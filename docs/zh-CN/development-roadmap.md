# PytaruiX 开发路线

更新日期为 2026-11-07。本路线用于规划独立框架、体积与性能优化、当前 ECL 接入及后续发行。文档规划已获授权，新增功能阶段的实施状态在各阶段方案中记录。

## 1. 产品与工程目标

PytaruiX 作为独立 Python 包提供 Tauri 桌面能力，维护清晰的 Python API、类型、原生线程与资源语义、前端桥及可追溯 wheel。ECL 作为主要消费方验证真实应用规模下的可用性，业务代码留在 ECL。

长期保留完整覆盖 Tauri 可用能力与逐步适配官方插件的目标。近期先建立可重复构建、可信能力裁剪、性能基线和当前 ECL 接入闭环，再按依赖补齐接口。

通用工程与验收依据为 [项目规范](../../AGENTS.md)。第一至第十阶段的授权、当时范围和历史结果保留在 [实施记录](implementation-plan.md)，历史指南中的 ECL 命令数量、绝对路径和补丁仅代表对应阶段快照。

## 4. 包结构与发行选择

当前推荐沿用一个 Python 包和一套公开 API，以构建 features 表达原生能力。

| 构建用途 | 能力选择原则 | 验收重点 |
| --- | --- | --- |
| 默认通用 wheel | 以当前默认桌面、对话框与 PNG/ICO 为基线；改变默认集合另行确认 | 安装即用、模块导入、能力报告与默认示例 |
| 开发/完整验收构建 | 在选定桌面基线上显式开启 devtools、tray-icon 等需要的能力 | 开发调试和九组原生场景 |
| 精简源码或 ECL 候选 | 从真实调用选择窗口、权限、图像、插件与调试能力 | 依赖树、关闭能力拒绝、宿主真实流程 |

编译 feature 由构建时选择。Python extras 无法切换已下载 wheel 中的原生实现；公开索引也需要清楚的变体选择方式。首批实验使用独立本地目录、环境和摘要标识，默认不增加多个公开发行包。

若测量证明分别发行原生插件或多个包变体有价值，再评估加载 ABI、版本协同、安装解析和维护成本。Pydantic 可选化、ABI3 与无 GIL Python 同样作为后续独立评估项。

## 5. ECL 集成原则

- 使用当前 ECL 工作区、frontend 子模块及运行时维护补丁建立调用清单，记录相关源码摘要。历史 216 个命令及第九阶段迁移文件清单需要重新核对。
- 对照当前命令签名、窗口/事件、文件对话框、图像、权限、配置、开发者工具、托盘和冻结 Worker；对每项分别记录需要、已支持、差异与验收入口。
- 框架提供通用接口和正确的安全/生命周期语义；ECL 维护业务、主题、账户数据与插件授权流程。
- 使用隔离副本与数据目录。迁移计划须覆盖当前 EasyTier、插件原生窗口、Python Worker、打包和退出，不只验证主窗口能显示。
- CSP、隔离、自定义协议及平台专属行为按实际需求单列。独立包版本、ECL 依赖与构建清单同步更新。
- ECL 源码与发行物分别验收，单文件/目录包和各平台分别记录。当前包引用与替换在 ECL 获得实施确认后完成。

## 6. 后续通用能力顺序

在优化与当前集成闭环基础上，按依赖推进。

1. 完整菜单角色、默认菜单及现有托盘的跨平台差异与生命周期证据。
2. Window/WebView Builder、导航、新窗口、下载、请求和嵌入相关接口。
3. App/Builder/Context、状态、事件与生命周期完整性；IPC 确认、背压和取消需独立契约。
4. 资源、自定义协议、CSP、ACL、隔离和构建集成。
5. 官方插件按独立版本逐个适配，优先级由真实消费需求与覆盖依赖决定。
6. 实验性接口、移动运行时、ABI 与架构扩展分别建矩阵。

每批同步公开类型、迁移契约、人工账本与平台证据。PyTauri Python 兼容包仍保留为长期可选路线，当前明确维护的旧前端协议继续按契约处理。
