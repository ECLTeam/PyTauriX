# 第十一阶段方案 · 体积与性能基础

日期为 2026-11-07。状态：基线已执行并记录在 [体积、导入与 Context 基线](performance-baseline.md)；feature 边界修正、[release 参数实验](release-profile-experiment.md)与 IPC 基准已完成，默认 profile 已采用 `opt-level="s"` + `codegen-units=1` + thin LTO，候选 wheel 已验证。本方案其余代码、构建和功能变更仍待明确实施确认。

## 1. 目标与范围

建立当前源码的体积、导入、启动和 IPC 基线，修正精简构建的上游 feature 边界，比较 release 配置，形成可重复构建和验收的候选 wheel。

长期目标与后续包结构见 [开发路线](development-roadmap.md)，工程与检查规则见 [项目规范](../../AGENTS.md)。默认功能调整、资源加载替换、IPC 协议/调度改造、依赖升级、ABI3、独立插件发行和 ECL 原仓库迁移分别需要后续方案。当前实验保留已有公开导入与新旧前端契约。

## 3. 方案比较与推荐

| 方案 | 工作内容 | 收益与取舍 |
| --- | --- | --- |
| A · 仅测量 | 建立基线与报告 | 最容易隔离行为，裁剪与包体改善继续后置 |
| B · 测量加构建优化 | 基线、上游默认 features 控制、release 参数对比、候选 wheel | 能直接验证体积与可用性，改动集中在构建边界；推荐 |
| C · 同时改资源和 IPC | 在 B 上加入资源加载、协议/调度优化 | 跨越安全、线程和宿主语义，难以归因，需要更多独立验收 |

推荐 B。采用一套源码和公开 API，沿用当前通用默认能力，开发和精简构建通过显式 features 选择。B 的选择与实施待本方案确认，首轮数值不预设为承诺收益。

## 5. 实施顺序

### 5.1 先固化当前源码和托盘状态

1. 检查分支、索引、未跟踪内容、已安装 wheel 和原生模块真实路径，记录工具链与锁文件摘要。
2. 当前仓库尚无提交，使用源码文件清单和 SHA-256 作为基线身份，排除 artifacts、target、缓存和已安装二进制。获得提交授权后再补提交身份。
3. 对照第十阶段方案、源码、能力报告与现存日志，列出已证实与待验收项；保留 Windows/POSIX、GUI、打包的区别。
4. 新建 `artifacts/phase11/` 批次目录，保存 baseline、experiments、candidate 和 reports。每个构建记录自己的源码/配置/锁文件身份，不共用来源不明的 wheel。

### 5.2 建立优化前基线

1. 在相同解释器、目标和锁文件下实际构建当前默认与开发能力的 release wheel，保留构建输出及大小分解。
2. 在独立环境安装 wheel，确认导入路径来自安装目录；记录新环境安装产生的运行时依赖与总体占用，区分共享文件与框架自身。
3. 构建并测量最小功能组合，记录明确的未支持项；初始构建失败同样保留，不用临时开启全部功能取得成功。
4. 在独立进程运行导入与真实桌面基准，保存原始样本、错误与资源收尾结果。
5. baseline 完成后先生成结果摘要，再开始裁剪；不得把已经裁剪的构建作为优化前基线。

### 5.3 修正 feature 边界

1. 核对当前 tauri/default 的真实内容与全部依赖来源，区分 Wry 运行时、平台功能、动态 ACL、资源压缩和插件需要。
2. 从 workspace 一致控制上游默认 features，bridge 与 bindings 只启用明确需要的集合；本包 default 维持现有使用能力。
3. 默认、开发、最小和最小托盘组合分别检查最终依赖树。判断关闭 feature 是否关闭对应上游依赖，检查是否存在插件再次启用的路径。
4. 验证导入、能力报告、关闭能力的明确拒绝与开启能力的真实行为，保持宿主 ACL、旧协议及错误恢复。
5. 若某项上游默认能力确为通用基线或平台必需项，显式启用并记录原因；不为减小数字破坏权限和桌面行为。

### 5.4 比较 release 参数

1. 以 feature 修正后的同一源码和同一能力集合为共同起点，先比较当前 release 与仅符号裁剪。
2. 再分别比较 `opt-level = "s"`、`codegen-units = 1` 与 thin/fat LTO。先单因素，再组合表现合适的候选，记录每次配置。
3. `opt-level = "z"` 仅在前述结果需要时补测；panic 策略和 CPU 专属目标优化不列入本阶段默认参数实验。
4. Windows 排障符号单独保存，Linux/macOS 分别评估 strip 与诊断方式。Debug/开发构建与 release 大小分别记录。
5. 同时比较编译耗时、内存、导入/首屏、IPC 与错误处理。没有稳定体积收益或造成可观察退化的组合不作为候选。

### 5.5 候选收敛与交付

1. 按平台选择有证据的候选配置，生成默认与需要的开发/精简 wheel，并从当前 sdist 实际重建。
2. 执行项目规范要求的全量质量、适用 feature 与原生桌面验收，补上构建和类型相关回归。
3. 更新基线报告、构建组合说明、能力与阶段状态，列明收益、噪声、取舍、未执行平台和下一批建议。
4. 根据现有 ECL 迁移脚本和当前源码做调用适配差距调查，产出后续集成任务；不直接套用第九阶段补丁。
5. 当前阶段交付为本地可审阅源码、报告和候选产物；提交、远程构建及公开发行按各自授权执行。

## 6. 构建与行为矩阵

以下组合是实验起点，均需核对目标平台依赖。新增必需项写入组合说明，不能以未记录的额外 features 完成验收。

| 组合 | 构建参数 | 主要检查 |
| --- | --- | --- |
| 通用默认 | 当前 default | 现有默认示例、dialog、PNG/ICO、动态窗口/权限、无托盘时的能力拒绝 |
| 开发/全场景 | default 加 `devtools,tray-icon` | 九组现有桌面场景、开发者工具与托盘 |
| 最小桌面 | `--no-default-features --features wry` | 核心窗口/IPC/事件、显式权限样本、可选功能拒绝 |
| 最小加托盘 | `--no-default-features --features wry,tray-icon` | RGBA 图标、菜单/托盘与资源释放，保留 PNG/ICO 未启用状态 |

Windows 优先使用 3.11 与 3.14 分别实际构建、安装与行为检查，基线实验先固定一个解释器完整比较，再核对另一版本。Linux/macOS 沿现有 CI 扩展构建与干净安装，各自保留 GUI 与平台专属效果证据；无远程时记录待执行条件。

第十一阶段沿用单任务 Rust 构建，不同时运行多组编译与 GUI 实验。精简组合在关闭 dialog/image/tray 时使用对应拒绝用例；不把不适用的功能场景误计为通过。

## 7. 测量方法与报告字段

### 7.1 大小与构建

- 每个产物记录源码与锁文件摘要、构建命令、解释器/ABI/目标、有效 features、工具链、时间及 SHA-256。
- 输出 wheel 归档大小、内部各文件压缩前后大小、安装后的框架目录、运行时依赖环境与 sdist 大小；测试宿主发行包另作一列。
- 比较 release 产物，保留 PDB 等诊断文件大小；全新 target 编译与增量重编译分别记录，不把缓存差异当优化收益。
- 记录实际平台 WebView 依赖及其来自系统或独立安装的方式，不将系统预装运行时体积归零后宣称所有用户安装成本。

### 7.2 导入与首屏

- 分别测解释器空启动、`import pytaruix`、Context 准备、原生 build、窗口可见和真实前端首次有效 IPC；使用单调时钟，说明跨进程握手方法。
- 重复启动至少保留 20 个独立进程样本及预热记录，报告样本数、原始值、P50/P95 和波动。失败/超时单列，不能从样本中静默删除。
- 首次用户数据目录启动与重复启动分开。未控制 OS 文件缓存的结果标为首次/重复运行，不宣称真实冷缓存测试。
- 窗口可见使用实际原生事件或系统观测确认，首次 IPC 使用当前前端桥。仅 DOM 加载不等于窗口已可见或宿主已可用。
- 固定 frontendDist 数据集的文件数、总字节与摘要，至少覆盖小示例和当前 ECL 前端同规模样本；记录准备时间和峰值/稳定内存。

### 7.3 IPC、流与收尾

- 覆盖空/小 JSON、Pydantic、64 KiB 与 1 MiB 二进制、Channel 连续推送、并发命令及失败后正常调用。
- 普通调用建议每批 1000 次，大载荷每批 100 次，每场景至少 5 批；根据总耗时明确调整样本数并在报告写出。先预热，限量在途请求，避免用无界队列制造结果。
- 记录端到端延迟、P50/P95、吞吐、错误、峰值内存和退出后存活资源；Channel 接收数与序列由前端核对，send 返回不算接收确认。
- 注册、监听、窗口来源与权限通过正常链路执行。涉及并发、退出或错误的样本保留资源释放与后续恢复检查。

### 7.4 候选选择

首轮建立噪声范围后，依据样本和场景记录本阶段的数值判定门槛，作为候选配置的比较依据；对外性能承诺另行确认。每个候选以相同源码、能力和环境比较，说明节省的绝对字节与比例，以及启动、IPC、构建和内存变化。

功能与安全检查为必须通过的条件。性能差异位于噪声范围时按无明确改善记录；本阶段允许以完善基线和正确能力边界收口，不承诺某个预设减小比例。

## 8. 验收与恢复

| 验收项 | 通过依据 |
| --- | --- |
| 基线可重复 | 新环境按命令安装并生成报告，产物/源码/依赖身份明确 |
| 裁剪可信 | 四类组合有效依赖与声明一致，关闭能力拒绝和开启能力实际行为通过 |
| 默认契约 | Python/ffi/类型、新旧前端协议、来源权限、错误恢复与生命周期通过 |
| 候选收益 | 同源参数对比有原始样本和噪声，所选参数有清晰取舍 |
| 包可重建 | 独立 wheel 与当前 sdist 重建实际通过，安装后不依赖源码路径 |
| 平台结果 | 每个平台构建、安装、GUI 独立列明，未执行保留具体条件 |
| ECL 后续入口 | 当前调用与差距清单形成，历史证据与本轮结论区分 |

本阶段涉及 features、构建与公开能力边界，最终执行项目规范 8.2 的 Python 全量质量/行为、Rust 格式与指定组合 Clippy、覆盖账本、wheel/sdist 检查，另按 8.3 完成适用原生场景。

失败候选保留日志与配置，先回到上一份同源通过产物再调查；恢复基于本批次明确改动清单，不清空工作区或用户数据。基准进程有超时和关闭路径，仅终止自行记录的进程。
